## 2. Findings in detail

### A50 — HIGH — config loader is all-or-nothing: one unknown key resets everything to defaults
**File:** `config.py:208-243`

```python
telescope = TelescopeConfig(**data.get('telescope', {}))      # 208
...
guiding = GuidingConfig(**data.get('guiding', {}))            # 224
...
except Exception as e:                                        # 240
    logger.error(f"Error loading config: {e}")
    _config = CerberusConfig()                                # 242  <- whole config replaced
    return _config
```
Every section except `camera` is built with `Dataclass(**dict)`, so any key that is not a dataclass
field raises `TypeError`, which the blanket `except` turns into a *complete* default configuration.

**Verified empirically** (`scratchpad/cfgtest.py`, real `config.py`): adding one key
`guiding.some_old_key` produced
`telescope.host=<default> | filters={} | focus_positions={} | buffer_size=100` with only an ERROR log line.

**Failure scenario:** an operator adds a comment-like key, a field is renamed in a future dataclass
edit, or an older/newer `config.json` is copied in. The app starts "fine", but: `FilterWheel(filters={})`
→ `filter` property reports `"Position N"` and `set_filter('r')` raises `ValueError: Unknown filter`;
camera ring buffer falls from 500 to 100 frames (NOTES.md says 100 Hz then corrupts frames);
all calibrated focus positions vanish; `_save_config()` later **persists the defaults**, destroying the
original file.

**Fix:** filter kwargs to known fields, warn on the rest, and never fall back to defaults for a *parse*
error of an existing file:
```python
def _build(cls, section: dict, name: str):
    known = {f.name for f in dataclasses.fields(cls)}
    unknown = set(section) - known
    if unknown:
        logger.warning(f"config[{name}]: ignoring unknown keys {sorted(unknown)}")
    return cls(**{k: v for k, v in section.items() if k in known})
...
except json.JSONDecodeError as e:
    raise RuntimeError(f"config.json is not valid JSON: {e}")   # fail loudly, do not silently default
```

### A51 — HIGH — `update_status()` blocks the GUI thread on TCS + DCAM every second (BUG #46 confirmed) and shares an unlocked TCS socket
**File:** `api/cerberus.py:1539-1637`; callers `gui/app.py:417-430` (Tk `after(1000)`), `gui_qt/app.py:64,278-283` (QTimer), and synchronously from `set_camera_property()` at `api/cerberus.py:297`.

What one call does, in order, on the calling thread:
1. `self.telescope.get_focus()` (1555) → `REQSTAT`; `get_position()` (1556) → `REQPOS`;
   `get_status()` (1557) → `REQSTAT` **again** (duplicate of step 1; `get_focus()` is
   `get_status().focus_mm`, client.py:263-264). Each is `haletcs._send_command`: non-blocking stale
   flush, `sendall`, then a blocking `recv` loop bounded only by the socket timeout
   (`telescope.timeout_seconds = 30.0`, config.json:5 → client.py:88 → haletcs client.py:183).
   **Worst case ≈ 90 s** if the TCS stops answering; typical = 3 network RTTs.
2. `self.filterwheel.filter` (1560) → ctypes `EFWGetPosition` (ms, but unlocked — see A58).
3. Per camera (1576-1577): `get_exposure()` and `get_property('SENSOR_TEMPERATURE')` → each
   `DCamLock.acquire_property(timeout=1.0)` (controller.py:736) + `dcamprop_getvalue` (a synchronous
   driver call; BUG #46 reports multi-second stalls during long exposures). The property lock is also
   held by `set_property()` while it re-reads all ~88 properties (controller.py:722-723, 900-921), so
   a GUI settings change can make the poll wait the full 1 s per read. **Bound ≈ 2 × (1 s + driver)
   per camera.** `get_all_params()` (1579) is a cached copy; `get_frame_rate()` is cached.
4. `_notify_status_change()` (1637) → `self.state` deep copy under `_state_lock` (can wait behind
   A52) + every status callback, synchronously.

**Concurrency hazard:** `TelescopeController` has `_cmd_lock` for the command socket only
(client.py:105, 214, 240, 396). The **status socket is unlocked** (client.py:252-267, 347-377) and is used
concurrently by: this GUI-thread poll; the focus thread (`wait_for_focus` client.py:289-343 polls every
0.5 s for up to 60 s; `capture_single_to_fits` 472-473; `FocusLoop.run` 359); `offset_focus` (836);
`save_current_filter_focus` (1405). Two threads interleaving `REQSTAT`/`REQPOS` on one TCP stream mix
responses — haletcs's "flush stale data" workaround at client.py:222-232 is the tell-tale.

**Fix:** (i) drop the duplicate query — derive focus from the one `get_status()`; (ii) add a
`_status_lock` in `TelescopeController` (or a single `_io_lock`) around every status-socket call;
(iii) never call `update_status()` from a GUI timer: run it on a dedicated poller thread and let the
GUI consume `api.state` / the status callback (see §4); (iv) make `set_camera_property()` refresh only
that camera's cached params instead of calling the full poll.

### A52 — HIGH — blocking hardware I/O while holding `_state_lock` stalls the camera thread
**File:** `api/cerberus.py:768-779` (`connect_telescope`), `189-193` (`connect_camera`).

```python
with self._state_lock:                                   # 768
    self._state.telescope_connected = success
    if success:
        self._state.telescope_focus = self.telescope.get_focus()      # 771  REQSTAT (≤30 s)
        pos = self.telescope.get_position()                           # 772  REQPOS  (≤30 s)
```
and
```python
with self._state_lock:                                   # 189
    ...
    cam_state.exposure = controller.get_exposure()       # 193  DCAM property lock (≤1 s) + driver
```
`_on_camera_frame()` acquires `_state_lock` **for every frame on the capture thread** (1705-1709), and
the controller calls it from inside `_process_frame` (controller.py:414-420) before the next
`wait_capevent`. While the lock is held for a slow TCS reply, capture stops; at 100 Hz with a 500-frame
ring buffer, >5 s of blocking overwrites unread frames (NOTES.md). Every `api.state` read (all GUI
panels) also freezes.

**Failure scenario:** camera 0 is recording; operator (re)connects the telescope from the toolbar
(runs in a thread, but the lock is global); TCS is slow → frames dropped/corrupted for the duration.

**Fix:** query first, assign under the lock:
```python
focus = self.telescope.get_focus(); pos = self.telescope.get_position()
with self._state_lock:
    self._state.telescope_connected = success
    self._state.telescope_focus = focus
    if pos: ...
```
Same pattern for `connect_camera` (read `controller.get_exposure()` before the `with`).

### A53 — MEDIUM — wrong `EXPTIME` in focus-loop FITS headers
**File:** `api/cerberus.py:466`; `focusloop/focus_sequence.py:230`.

`FocusLoop._take_focus_image` sets the exposure directly on the controller
(`self.camera.set_exposure(exposure)`, 230), bypassing `api.set_exposure()`, so
`_state.cameras[i].exposure` is not updated. `capture_single_to_fits` then writes
`exposure = cam_state.exposure or controller.get_exposure()` (466): the cached value is truthy and
stale, so the fallback never runs. The only thing that refreshes the cache is the GUI's 1 s poll, so
the header is right or wrong depending on timing. With per-filter multipliers (1 s vs 10 s for u/Ha)
the error is large, and `FocusAnalyzer`/downstream users read `EXPTIME`.

**Fix:** in `capture_single_to_fits` prefer hardware: `exposure = controller.get_exposure() or
cam_state.exposure`; and/or have `FocusLoop` call `self.api.set_exposure(exposure,
camera_index=…)` when an API is present.

### A54 — MEDIUM — callback contract: locks held during callbacks, callback threads undocumented
**File:** `api/cerberus.py:150` (`_callback_lock = threading.Lock()` — not an RLock), `1731-1736`,
`1742-1747`; `hardware/camera/controller.py:122-124, 414-420`.

* Frame callbacks are invoked on the **camera capture thread**, inside the controller's
  `_callback_lock` *and* the API's `_callback_lock`. A callback that calls `api.on_frame()` /
  `remove_frame_callback()` deadlocks the capture thread; a slow callback delays the next
  `wait_capevent` directly (the `_callback_skip` throttle only helps above 100 Hz, controller.py:525-527).
* Status callbacks are invoked **synchronously on whichever thread called the API method** — the Tk
  thread (timer poll, `set_exposure`), a `connect_thread`, the filter-change thread (`set_filter`
  → 1044), the focus thread (`run_focus_loop` finally → 1383) — never the camera thread. They run
  under `_callback_lock`, so `remove_status_callback()` from inside a status callback deadlocks.
* The Qt GUI does `QTimer.singleShot(0, …)` from those worker threads (gui_qt/app.py:233), which Qt
  does not permit from a non-QThread (GUI reviewer's scope, but it stems from this contract).

**Fix:** snapshot the callback list under the lock, invoke outside it
(`for cb in list(self._status_callbacks): …`), or use `RLock`; document threads (see §4).

### A55 — MEDIUM — legacy single-camera aliases are broken or silently wrong
**File:** `api/cerberus.py:126, 255-277, 365-375, 678, 737, 742-744`.

* `self.save_thread`/`self.save_queue` are **never initialised in `__init__`**; they are first
  assigned in `start_saving()` (678) for the first camera only. `is_saving()` (742-744) therefore
  raises `AttributeError: 'CerberusAPI' object has no attribute 'save_thread'` until the first save,
  and afterwards reports only camera 0.
* `set_binning()` (265), `set_trigger_source()` (277), `capture_single()` (375) use `self.camera`
  (126 = first camera) and take no `camera_index`; `gui/panels/camera_settings.py:125` calls
  `set_binning` (that panel is currently not instantiated, but the API is public).

**Fix:** initialise `self.save_thread = None; self.save_queue = None` in `__init__`, implement
`is_saving(camera_index=None)` from `_state`, and add `camera_index` to the three camera methods
(delegating to `set_camera_property`).

### A56 — MEDIUM — `start_saving()` twice on the same camera orphans a save thread
**File:** `api/cerberus.py:549-588, 661-678`.

The only precondition is `cam_state.streaming` (574-575). A second call creates a new queue, points
the controller at it (588), starts a new `OptimizedSaveThread` (674) and overwrites
`_save_threads[idx]` (673). The previous thread is never `stop()`ped: it loops forever on
`while self.running or not self.save_queue.empty()` with a 1 ms `get` timeout (save_thread.py:236-241),
its partially-filled cube is never flushed, and its `ThreadPoolExecutor` stays alive.

**Fix:** at the top of `start_saving`: `if cam_state.is_saving: logger.error(...); return False`
(or call `self.stop_saving(camera_index)` first).

### A57 — MEDIUM — stop path blocks the caller for up to ~62 s and the GUI double-stops
**File:** `api/cerberus.py:335-357, 717-720`; `hardware/camera/controller.py:574-577`;
`gui/panels/camera_controls.py:281-300`; `gui/app.py:504-512`.

`stop_streaming()` = controller stop (`sleep(0.2)` + capture lock ≤2 s, controller.py:574-577) +
`time.sleep(0.2)` (354) + `stop_saving()` → `save_thread.join(timeout=60)` (720). With 1000-frame
full-frame cubes (~19 GB) the final flush can genuinely take tens of seconds — on the Tk thread.
If the join times out, the still-running thread is deleted from `_save_threads` (A56 orphan) and its
stats are read mid-flight. The GUI then reads `cam_state.is_saving` from a **copy taken before the
call** and calls `stop_saving` a second time (camera_controls.py:298-300; app.py:509-512) — harmless
but shows the state-copy contract is misunderstood (cf. BUG #45).

**Fix:** make `stop_saving` return immediately after `stop()` and expose `wait_for_save_complete(timeout)`,
or run the join on a worker and report completion via the status callback; remove the redundant GUI
sleeps.

### A58 — MEDIUM — `_filterwheel_lock` is bypassed by every reader and by the focus loop
**File:** lock only at `api/cerberus.py:1025`; unlocked EFW calls at 459 (`capture_single_to_fits`),
609 (`get_current_filter`, **called from the save thread** at cube boundaries), 909, 1075
(`get_filter`), 1560 (`update_status`, GUI thread), 1697; `focusloop/focus_sequence.py:376`
(`self.filterwheel.goto()` from the focus thread, also bypassing `_state.current_filter`).

The lock's own comment says "hardware has no internal locking". `EFWGetPosition` from the GUI poll
while `EFWSetPosition`/`wait_for_move` runs on the filter thread is exactly the case it was added for.

**Fix:** route all reads through a small `_fw_read()` helper that takes the lock (it is a plain `Lock`
— use an `RLock` since `set_filter` reads `.filter` inside it), and have `FocusLoop` call
`api.set_filter(name, apply_focus=False)` when an API is present.

### A59 — MEDIUM — filter-name case mismatch and `"unknown"` keys in `focus_positions_mm`
**File:** `api/cerberus.py:1035, 1094, 1355-1363`; `filterwheel/filterwheel.py:101-102`;
`config.py:143-153`; `config.json:34-51`.

`FilterWheel.filter = name` matches case-insensitively (filterwheel.py:101-102) so
`set_filter("ha")` succeeds, but `_state.current_filter = name` stores the caller's spelling (1035)
and `config.get_filter_focus_position("ha")` is a plain dict lookup — `"Ha"` is not found, no focus
is applied, and the next focus loop writes a **new** `"ha"` key next to `"Ha"`. With no filter wheel,
`fname = filter_name or self._state.current_filter or "unknown"` (1355) persists `"unknown": <mm>`
into config.json (and `_save_config` now round-trips it forever).

**Fix:** canonicalise through the wheel: after the move, `self._state.current_filter =
self.filterwheel.filter`; in `run_focus_loop` skip persisting when the name is unknown.

### A60 — MEDIUM — unlocked, non-atomic `_state` reads (BUG #13 still present)
**File:** `api/cerberus.py:216-217, 352, 421, 457, 470, 574, 607, 615-653, 811, 834, 1028, 1041,
1094, 1146, 1301-1314, 1355, 1363, 1400-1404, 1659, 1695, 1761-1773`.

Most are benign single-field reads, but `get_telescope_data()` (615-653) is called by the **save
thread** at every cube boundary and reads ~15 telescope fields one by one while `update_status()`
assigns them one by one under the lock (1594-1636). A cube header can therefore carry `TELDAY` from
one poll and `TELUTC` from the next, or a focus/tube-length pair from different `REQSTAT` replies; if
the focus read failed once (`telescope_focus=None`, 1615) the whole status block is omitted (626-627).

**Fix:** build the two dicts under `_state_lock` (it is cheap), or have `update_status` swap in a
single immutable snapshot object.

### A61 — MEDIUM — guiding engine: synchronous TCS move on the GUI thread; averaging window defeated
**File:** `guiding/engine.py:155-179, 181-185, 107-125`; `gui/panels/image_display.py:302, 633-662, 1040-1041`.

* `add_measurement()` → `_update_guiding()` → `_apply_guiding_correction()` → `self._apply_correction`
  = `api.move_offset()` (image_display.py:1041) → `TelescopeController.move_offset` under `_cmd_lock`
  → haletcs `_send_action_command`, and "a command channel blocks until move is complete" (haletcs
  client.py:662). `add_measurement` is called from `_update_fwhm` (633/662), which runs in
  `_display_loop`, a Tk `after` callback (302) — i.e. the **main thread**. Every correction freezes the
  GUI for the move duration (≤30 s socket timeout) and contends with the focus loop for `_cmd_lock`.
* `_trim_history()` keeps `max(100, min_samples*10)` = 100 entries (183). With `averaging_window_seconds
  = 15`, any measurement rate above ~6.7 Hz turns the "15 s average" into "last 100 samples"; at 30 Hz
  that is 3.3 s. `_compute_average_position()` then makes decisions right after a correction from only
  `min_samples` = 3 points (117-121), because the history was cleared (175). Commit 19c8541 ("Fix
  guiding runaway") suggests this matters.
* No thread-safety at all — acceptable only while everything stays on the GUI thread; document it.

**Fix:** dispatch the correction to a worker (`threading.Thread(target=self._apply_correction, …)` or a
queue) and suppress further corrections until it reports back; size the history by time
(`max_entries = window_seconds * expected_rate` or trim by timestamp); after a correction require
either `min_samples` **and** a minimum settle time.

### A62 — MEDIUM — the API never uses `config.focusloop`; defaults are wrong for this telescope
**File:** `api/cerberus.py:1156` (`self.run_focus_loop()` with `config=None`);
`focusloop/focus_sequence.py:34-36, 157`; `config.json:55-57` vs `44-51`.

`FocusLoopConfig()` defaults are 30–45 mm in 2.5 mm steps (7 positions); `config.json` says 0.25 mm
steps and the calibrated best focus for every filter is 25.8–27.0 mm — **outside** the default scan
range. `calibrate_filter_focus()` would therefore drive each filter through a useless scan and write
extrapolated parabola vertices into `focus_positions_mm`. The Tk GUI avoids this only by building its
own `FocusLoopConfig` (focus_window.py:472-481); a new GUI using the API defaults will not.

**Fix:** in `run_focus_loop`, when `config is None`, construct it from `get_config().focusloop`
(`start_position_mm`, `end_position_mm`, `step_size_mm`, `exposure_time_seconds`,
`settle_time_seconds`, `auto_apply_best`, `exposure_multipliers`, `paths.focus_output_dir`).

### A63 — MEDIUM — `set_camera_property()` runs the full hardware poll; `set_property` re-reads everything
**File:** `api/cerberus.py:279-297`; `hardware/camera/controller.py:722-723, 900-921`.

Every property change (all of `gui/camera_settings_window.py:189-254`, `subarray_panel.py:194-197`
— five sets for one ROI) triggers `self.update_status()` synchronously (297): 3 TCS round trips +

**Fix:** after a set, refresh only `cam_state.params` from `controller.get_all_params()` and notify;
leave hardware polling to the poller thread.

## 4. API contract notes for a new GUI

**Threads that exist.** One `CameraThread` per camera (all DCAM calls; delivers frames); one
`SaveThread` per saving camera (+2 writer pool threads); whatever threads the GUI creates for
connect / filter / focus. The API itself creates no poller thread — `update_status()` is *pull*.

**Which thread callbacks fire on.**
* `on_frame(cb)` → **camera capture thread**, inside two non-reentrant locks, throttled to ~30/s above
  100 Hz (controller.py:525-527). Must return in ≪ 1/fps, must not touch widgets, must not
  register/remove callbacks, must not call blocking API methods. Copy the array if you keep it.
* `on_status_change(cb)` → **synchronously on the thread that called the API method** (GUI thread for
  `update_status`/`set_exposure`; your worker threads for connect/filter/focus; never the camera
  thread). Receives a fresh deep copy. Marshal to the GUI (`after`/`QMetaObject.invokeMethod` from a
  QObject that lives in the GUI thread — `QTimer.singleShot` from a foreign thread is not allowed).
  Do not call `remove_status_callback` from inside a callback (deadlock, A54).
* `run_focus_loop(on_progress=…)` → `on_progress` fires on the thread running the loop (yours).

**State access.** `api.state` returns a **snapshot copy** (cost: dict copy of ~88 camera params per
camera; fast, but it waits for `_state_lock`, which A52 can hold for seconds). It never updates in
place — re-read it; do not cache a copy across a call that mutates state (BUG #45). Prefer
`state.cameras[idx]` over the "first connected camera" convenience properties.

**Non-blocking / safe on the GUI thread (this snapshot):** `state`, `get_cameras()`,
`get_camera_params()` (cached copy), `get_display_frame(idx, timeout=0)` (use 0 — the default 0.1 s
blocks), `is_streaming()`, `is_gps_connected()`, `get_filter_focus_position()`,
`set_filter_focus_position(save=False)`, `on_*/remove_*` registrations, `abort_focus_loop()`,
`get_frame_rate` via state.

**Blocking — must run on a worker thread (bounds are worst-case from the code):**

| call | what blocks | bound |
|---|---|---|
| `update_status()` | 3 TCS round trips + 2 DCAM prop reads/camera + callbacks | ≈90 s TCS + 2 s/camera (typ. 10s–100s ms) |
| `set_camera_property`, `set_exposure`, `set_binning`, `set_trigger_source` | property lock + `prop_setvalue` + re-read of all ~88 props; `set_camera_property` adds a full `update_status()` | 1 s lock + driver (+ `update_status`) |
| `get_exposure()` | property lock + `prop_getvalue` | 1 s + driver (can stall during long exposures) |
| `connect_camera()` | thread start, `dev_open`, defaults, params walk, warmup capture | ≤30 s (`_connect_event.wait`, controller.py:178) |
| `disconnect_camera()` | `stop_streaming` + thread join | ≈2.5 s + 5 s |
| `start_streaming()` | capture lock 3 s, `buf_alloc(500 frames ≈ 9.5 GB)`, align-to-second wait | ≤3 s + alloc + ≤1.1 s |
| `stop_streaming()` | 0.2 s + lock 2 s + `cap_stop`; then 0.2 s + `stop_saving` | ≈2.5 s + up to 60 s (A57) |
| `start_saving()` | cheap (spawns thread) but see A56 | ms |
| `stop_saving()` | `join(60)` on save thread (final cube flush) | ≤60 s |
| `connect_telescope()` | 2 TCP connects + 2 queries **under `_state_lock`** | ≤4×30 s (A52) |
| `set_focus()`, `offset_focus()`, `move_offset()` | command socket; TCS returns only when the move completes; `_cmd_lock` shared with guiding/focus | ≤30 s each |
| `get_focus()` | `REQSTAT` | ≤30 s |
| `set_filter()` | wheel move (`wait_for_move` ≤30 s) + optional `set_focus` under `_filterwheel_lock` | ≤60 s |
| `get_filter()`, `get_available_filters()`, `connect_filterwheel()` | ctypes EFW calls (+0.5 s sleep on connect) | ms–0.5 s |
| `capture_single()`, `capture_single_to_fits()` | capture lock 5 s + `wait_capevent(timeout_ms)` + 2 TCS queries + FITS write | ≤5 s + exposure/30 s + 60 s |
| `run_focus_loop()`, `calibrate_filter_focus()` | minutes (moves, exposures, SExtractor subprocess without timeout) | unbounded |
| `connect_gps()` | device open/ioctl | fast |

**What a GUI must do to stay responsive.**
1. Never call `update_status()` from the GUI timer. Run a poller thread
   (`while not stop: api.update_status(); sleep(interval)`) and render from the status callback /
   `api.state`. Until A51/A52 are fixed, expect that thread to stall for the TCS timeout.
2. Put every call in the blocking table on a worker (thread pool or `QThread`), disable the control
   while it runs, and re-enable from the resulting status callback rather than from a sleep.
3. Marshal all callbacks to the GUI thread; keep frame callbacks trivial (put the frame in a
   1-slot queue; do FWHM/photometry on a worker, not on the capture thread and not on the GUI thread).
4. Guiding: call `GuidingEngine.add_measurement()` from one thread only, and give it a
   `correction_callback` that *enqueues* the move instead of calling `api.move_offset()` inline (A61).
5. Treat `api.state` as immutable and re-read after every API call; do not keep the pre-call copy.
6. Use `camera_index=` everywhere it exists; avoid `set_binning`/`set_trigger_source`/`capture_single`/
   `is_saving()` (A55) until they take a camera index.
7. Register status callbacks once at startup; never add/remove callbacks from inside a callback.
8. Do not rely on `state.errors`/`last_error` (A66) or `focus_loop_progress` (never updated; only
   `focus_loop_running` is meaningful) — use the focus loop's `on_progress`.
9. Importing `cerberus_coo` imports the Tk GUI (A71); a Qt GUI should import `cerberus_coo.api.cerberus`
   directly or the package `__init__` should stop importing `.gui`.
